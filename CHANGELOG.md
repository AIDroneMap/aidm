# Changelog

AIDM uses [Semantic Versioning](https://semver.org). AIDM started as a fork of ODX 3.8.4; since 0.2.0 a release names only its own version.

## Unreleased

### Added

- The Windows build makes either of the two variants of ADR 0006 (#125). `configure.py build` takes `cpu` or `cuda` and builds `cpu` when given neither, which is what the `windows-x64` job runs. The `cpu` variant configures OpenMVS and OpenSfM without CUDA, so neither turns CUDA on because a toolkit happens to be installed. The `cuda` variant takes the CUDA 12.9 toolkit from `CUDA_PATH`, the folder its installer sets, and stops when that folder has no `nvcc.exe` of release 12.9 or no MSBuild files of its own. It builds through the Visual Studio toolset `cuda=<toolkit>`, so Visual Studio needs no CUDA integration. OpenMVS and OpenSfM both require CUDA there, and their configure steps stop when they do not find it instead of building without it. OpenMVS keeps its maximum CUDA compatibility setting, as in the Linux GPU image, and OpenSfM keeps its own. After the build, `configure.py` reads the import tables of every program, DLL and Python module of the install folder and of `python/`. For `cuda` it copies into the install folder's `bin` the DLLs of the toolkit's `bin` that they import, and those the copies import in turn. It then lists the DLLs of the install folder's `bin` and stops a `cpu` build that holds or imports any CUDA DLL, a `cuda` build in which a file imports a CUDA runtime DLL that `bin` lacks or no file imports CUDA at all, and either build that ships the NVIDIA driver's `nvcuda.dll`. A build folder records its variant, and a build of the other variant in it stops and asks for `configure.py clean`. The OpenMVS recipe no longer downloads a stub `nvcuda.dll` from a reference project's release without a hash, and the SuperBuild no longer copies `cudart64*.dll` from any installed toolkit into every build. The Linux build does not change. Evidence: `tests/test_configure_variants.py` runs the DLL check on fake install trees made of fake PE files. Among its cases are a cpu tree that holds `cudart64_12.dll`, one that holds the stub driver and one whose tool imports `nvcuda.dll`, all of which fail. It also covers the copy of the runtime, the toolkit check, the variant arguments and the build folder record. The release dry runs linked in the pull request show the DLL check failing on a deliberate break and then the `windows-x64` job passing it.
- The Windows build pins its dependencies (#115). `SuperBuild/windows-deps.json` names release v1.0.0 of [aidm-windows-deps](https://github.com/AIDroneMap/aidm-windows-deps/releases/tag/v1.0.0) and the SHA-256 of the five files the Windows build and package steps read: the export zip, the GDAL wheel, the Python embeddable package, the ExifTool zip and the licence list. `configure.py build` downloads each file from that release, stops when a hash differs from the pin, unpacks the export and builds the SuperBuild with the export's toolchain and the `x64-windows-avx2` triplet. Every MSVC compile gets `/arch:AVX2` through the `CL` environment variable, and the SuperBuild stops at configure time when MSVC does not compile for AVX2. No workflow runs it yet. Evidence: `tests/test_configure.py` covers a wrong hash on a fake download, the pin checks and the unpacking of the export; the release dry run linked in the pull request builds the three Linux images.
- The Windows build lays out the package's own Python in `python/` (#119). `configure.py build` unpacks the Python 3.12.10 embeddable package of the pinned deps release, edits its `python312._pth` file to import `site` and to list `Lib\site-packages`, and installs the pins of `requirements.txt` there with pip `--target`, from wheels only. `vmem` is the exception: PyPI has it as pure Python source only, so `SuperBuild/windows-python-source.txt` pins the SHA-256 of its sdist, and a second pip call builds it with `--require-hashes`. pip runs on the Python that runs `configure.py`, which must be 3.12.10 for AMD64, the version and architecture of the embeddable package. There is no virtual environment any more. The embedded Python's `sqlite3.dll` is replaced with the export's, so that a process holds one SQLite. Then the package's Python runs a check with `PATH` limited to its own folder, the export's `bin` and the Windows folders: it prints every pin it finds installed in its `Lib\site-packages` and stops the build on a pin that is missing, has another version or lies elsewhere, on a failed import of numpy, or on a SQLite that does not open a database or is not loaded from the package. The SuperBuild on Windows compiles against the Python that runs `configure.py`, with the package's site-packages on its `PYTHONPATH`, and installs Python modules there. OpenCV gets that Python's headers and `python312.lib` explicitly: the deps export also holds a `python312.lib`, from the Python 3.12.9 its pybind11 port brings, which the vcpkg toolchain found first, so OpenCV left out its Python module. After the SuperBuild, the check runs again and also imports `cv2`, with the SuperBuild's `bin` on `PATH`; it runs even when the SuperBuild stopped, and the first failure is the one reported. When `python/` is laid out anew, for example after `requirements.txt` changed, the next build removes the install stamps of the SuperBuild's projects whose CMake install manifest lists a file in `python/`, OpenCV today, and runs the SuperBuild, so their Python modules are installed into the new layout without compiling again. It keeps doing so until a SuperBuild has finished. Evidence: `tests/test_configure.py` covers the `._pth` edit on the file as its publisher ships it, the two pip commands, the sdist pin of `vmem`, the requirements markers, the minimal `PATH`, the SQLite replacement, the `PYTHONPATH` of the SuperBuild, the order of the two checks, a new layout after a built SuperBuild, and the check itself on a fake site-packages; the release dry run linked in the pull request shows the check's lines in the `windows-x64` job.
- A Windows smoke test through the pinned released task API, with a separate start check for the engine version and absence of a CUDA driver. Evidence: `tests/test_windows_smoke.py` checks the shared settings, archive checks, task states, required outputs, Windows command arguments and failure verdicts, with recorded task API and georeferencing responses. The Windows runner first calls the script in #124.
- The design of the native Windows engine for 0.3: two variants, `windows-x64` and `windows-x64-cuda`, prebuilt dependencies from a repository of the project, and one archive assembled by the task API's release ([ADR 0005](docs/adr/0005-windows-dependencies-come-from-their-own-repository.md), [ADR 0006](docs/adr/0006-two-windows-variants-and-a-driver-floor.md), [ADR 0007](docs/adr/0007-the-native-package-is-one-archive-assembled-by-the-api-release.md), [design note](docs/design/windows-engine-0.3.0.md)). Nothing is built yet: the release workflow has no Windows job and `README.md` still says so. Evidence: the documents themselves; issue #15 carries the scope.

### Fixed

- OpenMVS passes its patch step on Windows (#154). Git for Windows checks out text files with CRLF line endings unless told otherwise, so on the hosted Windows runner `docker/patch_openmvs.py` did not find its line in `libs/Common/Config.h` and stopped the build. The OpenMVS recipe now clones with `core.autocrlf=false`, so the patch step reads LF bytes on every host, the weighted patch after it included. The width patch still stops when its line has changed, and it now says so when the file has CRLF line endings. The Linux images patch the same bytes as before. Evidence: `tests/test_openmvs_width.py` patches lines 114 to 135 of the pinned `Config.h` to the exact expected bytes and checks the CRLF stop. `SuperBuild/openmvs/test_patch.py`, which every OpenMVS build runs, clones a test repository with `core.autocrlf=true` in the global config, once with the recipe's clone settings and once without, and checks the bytes the patch reads. On the hosted Windows runner, [dry run 43668270544](https://github.com/AIDroneMap/aidm/actions/runs/43668270544) runs the OpenMVS patch step and starts its configure step, which then stops on OpenCV. The same run builds OpenMVS in the three Linux images.
- `AGENTS.md` says that the `windows-x64` job of `release.yml` runs `configure.py build` and names the Windows exception to the rule on repository files, with the four conditions of the [maintainer's override on PR #148](https://github.com/AIDroneMap/aidm/pull/148#issuecomment-6884219824) (#156). Evidence: the text matches `release.yml` on master and the override comment.
- On Windows, mvstexturing builds mapmap's SIMD code with `/arch:AVX2` (#155). [mapmap](https://github.com/dthuerck/mapmap_cpu), the MRF solver that mvs-texturing downloads, picks its 4 wide SIMD types with `__SSE4_2__` and its 8 wide functions with `__AVX__`. MSVC with `/arch:AVX2` defines `__AVX__` and `__AVX2__` but not `__SSE4_2__`, so mapmap compiled its 8 wide functions on a `float` type and the build stopped with 91 errors in `vector_math.impl.h`. On MSVC every C++ compile of mvstexturing now includes `SuperBuild/mvstexturing/MsvcMapmap.h` first. It defines `__SSE4_2__`, which AVX implies, so mapmap takes the same path as in the Linux amd64 image. That path calls `_mm_maskmove_si64`, the MMX instruction MASKMOVQ, which MSVC declares for 32 bit x86 only, so the header gives it a replacement that writes the same bytes. mapmap's sources are not changed or copied. The Linux build does not change. Evidence: the `windows-x64` job of dry run 43657782936 shows the errors without the change; `tests/test_mvstexturing_msvc.py` compares the replacement with the real MASKMOVQ under GCC, and the SuperBuild runs the same test on MSVC before mvstexturing builds; the release dry run linked in the pull request builds mvstexturing in the Windows probe and builds the three Linux images.
- OpenMVS finds OpenCV on Windows (#162). The OpenMVS recipe passed the Linux OpenCV folder, `lib/cmake/opencv4`, on every platform. On the hosted Windows runner CMake then found OpenCV's Windows pack config in the install folder, which has no binaries for the compiler, and OpenMVS stopped at its configure step on OpenCV. On Windows the recipe now passes `AIDM_OPENCV_DIR`, the one OpenCV folder that `SuperBuild/CMakeLists.txt` names, and stops with a clear message when that name is not set. The Linux recipe does not change. Evidence: the release dry run linked in the pull request, with the `windows-x64` job showing OpenMVS past `find_package(OpenCV)` and the three Linux image builds green.
- The OpenMVS weighted patch test compiles with MSVC (#168). `SuperBuild/openmvs/WeightedPatchTest.cpp` declared its scalar reference with the GCC attributes `noinline` and `optimize("no-tree-vectorize")`, which MSVC does not know, so the OpenMVS build step stopped on the hosted Windows runner (C2065 and C3861 at line 24) as soon as OpenCV was found. On MSVC the reference now gets `__declspec(noinline)`, and `#pragma optimize("", off)` surrounds it, so MSVC neither inlines nor vectorises the function the patched code is compared against. A scratch machine with MSVC 19.44 showed the reference as its own function, called from `compare`, with no packed arithmetic and no FMA, and no vectorizer entry for it. The test also needed a second fix: the patched header uses `#pragma omp simd`, which MSVC accepts only with `/openmp:experimental`, while OpenMVS gets plain `/openmp` from CMake's `FindOpenMP` (error C7660). On Windows the OpenMVS recipe now passes `OpenMP_RUNTIME_MSVC=experimental`, which CMake 3.30 and later turn into that flag. The same MSVC ignores the `reduction` clause of the first `omp simd` loop (warning C4849); the test's border cases decide the same as the scalar reference. The Linux build, the GCC declaration and the Linux test result do not change: the preprocessed test source is identical to before. Evidence: `SuperBuild/openmvs/test_patch.py`, which every OpenMVS build runs, preprocesses the test source for both compilers and checks the declaration each one gets, and checks the recipe's OpenMP argument; the rehearsal diagnostic is on [#168](https://github.com/AIDroneMap/aidm/issues/168#issuecomment-6891904983); the release dry run linked in the pull request, with the `windows-x64` job showing OpenMVS past this step and the three Linux image builds green.
- The Windows build finds OpenCV when the compiler is MSVC 14.5x, which CMake reports as `MSVC_VERSION` 1951 on the hosted Windows runner (#153). OpenCV 4.12.0 has no runtime name for that compiler. It installed its config in `lib` instead of `x64/vc17/lib`, and odm_orthophoto and OpenSfM stopped at configure without OpenCV. On Windows, `SuperBuild/CMakeLists.txt` now names the OpenCV architecture `x64` and runtime `vc17` in one place. The OpenCV recipe passes both names to OpenCV, and the OpenSfM and odm_orthophoto recipes read OpenCV's config from the folder made of them. After the OpenCV install, a build step stops the build when the config is not in that folder, with a message that names `MSVC_VERSION` and the folder. The Linux build does not change. Evidence: the release dry run linked in the pull request, with the Windows job, and the check step in `SuperBuild/cmake/OpenCVConfigDir.cmake`.
- The image builds install `six`, which the engine imports in `modules/photo.py` (#146). `six` was never pinned in `requirements.txt`. It came in through `python-dateutil`, which matplotlib pulls in, and `python-dateutil` 4.0.0 no longer depends on it. Without the pin the start check of all three images stopped with `No module named 'six'`, so the nightly of 2026-11-02 and every later one failed. `requirements.txt` now pins `six==1.17.0`. Evidence: the release dry run of this pull request builds the three images and runs their start check and smoke run; the pull request description links it. The unit tests run in the last published image, which already carries `six`, so they do not cover this change.
- The design note names the hosted Windows runner as it is: image `windows-2025-vs2026` with Visual Studio 2026, not Visual Studio 2022 (#150). Evidence: the probe log of dry run 43600116758, job `windows-x64`, and `BUILD-INFO.txt` of the deps release v1.0.0.

### Changed

- On Windows, GDAL, PROJ and PDAL come from the deps export, and ExifTool from the deps release (#120). The SuperBuild takes GDAL's headers and import library from the export, not from a folder of the GDAL wheel that holds neither. So PDAL finds `gdal_version.h` at configure, and dem2mesh, dem2points, fastrasterfilter and odm_orthophoto find `gdal_priv.h` at build. It stops at configure, naming the missing file, when the export lacks one of them. It copies the export's `share/gdal` and `share/proj` data folders into the install folder's `share`, without their CMake package files. `configure.py build` installs the GDAL wheel of the deps release, from its hash-checked download, into the package's site-packages, and stops when the wheel is not for the package's Python or its version is not the GDAL that `requirements.txt` pins for Linux. The PDAL Python bindings compile against the Python that runs `configure.py` and install into the package's site-packages, next to every other wheel. Before, they looked for Python's headers in the embeddable package, which has none. On Windows, the ExifTool recipe downloads the ExifTool zip of the pinned deps release, checked by its pinned SHA-256, and installs `exiftool.exe` with its `exiftool_files` folder; before, it downloaded a zip from a reference project's release without a hash. The check of the package's Python now also imports `osgeo`, and after the SuperBuild `pdal`, prints the SQLite version GDAL reports and stops when it is not the one the stdlib `sqlite3` runs. After the SuperBuild it also stops when the install folder lacks the GDAL or PROJ data folder. The Linux build does not change. Evidence: `tests/test_configure.py` covers the wheel's name and version against `requirements.txt`, its pip command, a new layout when the wheel changes, the data folder check, and the SQLite comparison on a fake `osgeo`; the release dry run linked in the pull request shows the lines of the check and the tools past their GDAL include in the `windows-x64` job, and builds the three Linux images.
- On Windows the SuperBuild builds Obj2Tiles from source (#118). The recipe clones the commit of the tag v1.5.0, restores its packages from the NuGet registry at the versions the project files pin, and publishes one self-contained `win-x64` executable with the .NET SDK of the build machine. It installs it as `bin/Obj2Tiles.exe`. Before, the Windows branch downloaded a prebuilt archive from a reference project's release page. The SuperBuild stops at configure time, naming `SuperBuild/cmake/External-Obj2Tiles.cmake`, when the pin is not a full commit hash, when `dotnet` is not on `PATH` or when its SDK is older than 10, the version the project targets. The install step prints the commit it built. The Linux and macOS branches are unchanged and still download the prebuilt archive; the Linux build is tracked in #164. Evidence: the `windows-x64` job of the release dry run linked in the pull request shows the `obj2tiles` tool built and installed in its build log, and the same run builds the three Linux images. Unit tests do not cover it, because they run in the last published image, which has the previous copy of `SuperBuild/`.
- The Windows build runs the SuperBuild with one pinned CMake, 4.4.5 from PyPI (#149). `SuperBuild/windows-cmake.txt` names the version and the SHA-256 of its Windows wheel. `configure.py build` installs it with `pip --require-hashes`, stops when the wheel differs from the pin, prints the path, the version and the generator of that CMake, and configures and builds the SuperBuild with it. Before, the SuperBuild ran with whatever CMake came first on `PATH`: 4.4.5 on the hosted Windows runner, 3.31 on other machines. 4.2 is the first CMake with a generator for Visual Studio 2026, the one on the runner. On Windows only, `configure.py` sets `CMAKE_POLICY_VERSION_MINIMUM=3.5`, so that gflags, dem2mesh, dem2points, laszip, lastools, mve and odm_orthophoto, which declare a minimum below 3.5, configure with CMake 4 and their `CMakeLists.txt` unchanged. The Linux build does not change. Evidence: `tests/test_configure.py` covers the pin checks, the pip command, a wrong hash on a local wheel, the commands that run the pinned CMake and the policy minimum; the release dry run linked in the pull request runs the Windows probe and builds the three Linux images.
- `configure.py` has two actions, `build` and `clean`. The `dist` and `vcpkg_export` actions and the options for an export URL, signing and a post-install command are gone; every address they downloaded from was a reference project's release. `requirements.txt` no longer has the Windows GDAL line, which took a wheel from such a release without a hash; the Linux and macOS lines stay. Evidence: `tests/test_configure.py` fails on any address in `configure.py` outside the AIDroneMap organisation and on any address in `requirements.txt`.
- ADR 0005 and ADR 0006 have amendments dated 2026-11-05 for the VC++ runtime zip, the two deps workflows, and the interface's AVX2-only check before download (#133). The engine's start check remains the last word on the processor, and the AVX2 and FMA minimum is unchanged. Evidence: review of the amendments against the [engine spec](docs/specs/0113-windows-engine-0.3.0.md), the [deps spec](https://github.com/AIDroneMap/aidm-windows-deps/blob/main/docs/specs/0001-first-deps-release.md) and the [interface spec](https://github.com/AIDroneMap/aidm-ui/issues/175).

## 0.2.0

Engine 0.2.0, released on 30 October 2026, ships with aidm-api 2.7.0 and the first tag of aidm-ui. The engine reports only its own version and no longer writes an `UPSTREAM_VERSION` file. The GPU image carries cuDNN and ONNX Runtime on the GPU. Compressed, it is 0.98 GB larger than the published 0.1.0 GPU image, by the layer sizes in the registry manifests; [#89](https://github.com/AIDroneMap/aidm/pull/89) gives the method and both sizes. Three stages use the GPU when the GPU image finds one: feature matching, densification, and the ONNX filters for sky removal and background removal. The Modal GPU test of the release workflow asserts each of the three.

### Changed

- Static tile generation and split-merge DEM blending use the shared memory limit to choose their worker counts (#29). Evidence: `tests/test_tiles.py` and `tests/test_dem_merge.py` check the worker limit under low available memory and compare output bytes with serial runs.
- CPU depth-patch matching projects coordinates and interpolates intensities in SIMD batches. Image reads remain guarded, and weighted NCC sums keep their original order. No fast-math flags or CPU targets change. Evidence: every OpenMVS build runs the scalar-equivalence checks in `SuperBuild/openmvs/WeightedPatchTest.cpp` and the patch checks in `SuperBuild/openmvs/test_patch.py`, which include that the patch step runs this edit after the arm64 width edit. Compiler diagnostics are recorded in [issue #53](https://github.com/AIDroneMap/aidm/issues/53). Performance has not been measured.
- Both images are built for modern CPUs. Every C++ tool, dependencies included, is compiled for x86-64-v3 (AVX2, FMA, BMI2) on x86-64 and for ARMv8.2-A on arm64, instead of Nehalem (2008, no AVX) and ARMv8.0-A. This reverses "The CPU image is built for a generic CPU" from 0.1.0. See "Hardware we build for" in `README.md` and [ADR 0001](docs/adr/0001-build-for-modern-cpus.md).
- The minimum CPU is now Intel Haswell (2013) or AMD Zen (2017) on x86-64, and ARMv8.2-A on arm64 (AWS Graviton 2, Ampere Altra, Apple M1, Raspberry Pi 5). Older CPUs, including the Raspberry Pi 4, are not supported.
- The new target does not make the engine faster. On an AMD Ryzen 9 9900X, against 0.1.0 built from the same commit, a full run takes the same time: 124.6 s against 125.1 s on Brighton Beach (18 images) and 302.3 s against 305.3 s on aidm-vineyard-small (73 images). Most stages change by less than 4%. The openmvs stage is 0.2% slower on aidm-vineyard-small and 6% to 8% slower on Brighton Beach (about 2 s of 29 s).
- `configure.sh install` replaces gcc and g++ with the wrappers in `docker/` when `CPU_TARGET_INSTALL=YES` is set. The old name, `PORTABLE_INSTALL`, no longer does anything.
- `--sky-removal` needs less memory, and its sky masks may differ from 0.1.0 by a few pixels on the mask edge. The sky filter runs in float32 and frees the full image as soon as it can, so a 20 megapixel image needs 0.75 GiB instead of 1.8 GiB. It also runs only as many images at once as fit in half the free memory. On Brighton Beach with 24 threads, the dataset stage peaks at 4.2 GiB instead of 10.4 GiB. Its masks there are byte-identical, but in a synthetic worst case 5 pixels out of 54 million flip, all on the mask edge.
- The build pins dem2points to commit `4527122` and Abseil to the `20260107.1` release, instead of following branches. Both are the code the branches pointed to, so the built code does not change. The Ceres version check now asks for 2.2.0, the version the build downloads, and two build settings that nothing read (`BUILD_opencv_gpu`, `GPU_INSTALL`) are gone.
- The build pins OpenMVS to commit `988e582f` instead of following branch `355` of WebODM/openMVS. It is the commit the branch has pointed to since February 2025, so the built code does not change. Evidence: the release dry run on the pinned source built all three images, passed their smoke tests and the GPU test: https://github.com/AIDroneMap/aidm/actions/runs/40825580422
- Both images build from base images pinned by digest instead of by tag: `ubuntu:24.04` for the CPU image, and `nvidia/cuda:12.9.1-devel-ubuntu24.04` and `nvidia/cuda:12.9.1-runtime-ubuntu24.04` for the GPU image. Each pin is the multi-arch index digest the tag pointed to on 29 October 2026, so the CPU image still builds for amd64 and arm64 from one line. Before, a tag that moved on Docker Hub gave two builds of the same commit different bases: on 29 October `ubuntu:24.04` moved between two builds of one job, the second build missed every cached layer and gave a different image (#56). Moving a base is now a pull request that changes the digest. Evidence: `tests/test_base_images.py` fails on any `FROM` line without a digest.
- Static tiles for orthophotos and DEMs are generated in parallel, with up to `--max-concurrency` workers. On Brighton Beach, orthophoto tiles take 0.55 s instead of 2.73 s and DSM tiles 1.08 s instead of 2.23 s.
- The DEM merge of a split dataset blends blocks in parallel, with up to `--max-concurrency` workers. On Brighton Beach with `--split 9`, the DSM merge takes 0.69 s instead of 1.07 s. Together with parallel tiles, the merge stage takes 11.0 s instead of 16.3 s.
- The orthophoto merge of a split dataset reads a submodel orthophoto or cut raster for an output block only when it can add a pixel to that block (#48). Before, each of the three merge passes read every submodel for every block, and a submodel outside the block came back as zeros. The merged orthophoto does not change. Evidence: `tests/test_orthophoto_merge.py` checks which blocks each raster is read for, including rasters whose edge falls on a block edge or 0.6 px from it, and that a four-submodel merge is byte for byte identical to master. Performance has not been measured.
- Frame extraction finds the SRT or GPX row for each frame by bisection instead of scanning every row. A 55-minute clip with a 100,000-row SRT extracts in 20.5 s instead of 62 s.
- Reading image metadata looks for the XMP packet in the first 1 MiB of each file and reads the rest only when the packet is not there. Loading the 18 Brighton Beach images reads 20.5 MB instead of 66.5 MB.
- With `--video-limit`, only the frames that are kept get their final JPEG encode. A 5-minute 4K clip extracts in 107 s instead of 132 s at the default limit of 500, and in 96 s instead of 131 s at a limit of 100.
- GPS to UTM conversion and `geo.txt` reprojection build one coordinate transformer per run instead of one per image or line. Stage times do not change measurably.
- Image builds no longer recompile the C++ dependencies when only Python code, tests or docs change. The release workflow keeps the layers in a registry build cache, `ghcr.io/aidronemap/aidm-buildcache`.
- The engine reports only its own version. The log banner, `--version` and the Software tag of GeoTIFF outputs now show `AIDM 0.1.0` instead of `AIDM 0.1.0 (ODX 3.8.4)`. The OpenSfM `report_version`, which the PDF report shows, is `0.1.0` instead of `0.1.0 (ODX 3.8.4)`. `log.json` loses its `upstreamVersion` field, and the `UPSTREAM_VERSION` file is removed. Changed outputs: the GeoTIFF Software tag, the PDF report, `log.json` and the OpenSfM report version. The origin of AIDM stays stated in `README.md` and in this changelog. Evidence: `tests/test_version.py` checks the version string, the `log.json` fields, the OpenSfM report line, and that no runtime source names an ODX version or reads `UPSTREAM_VERSION`. The passing unit check for this change: https://github.com/AIDroneMap/aidm/actions/runs/40655942137/job/122706878563
- The smoke tests and the Modal GPU test process [aidm-vineyard-small](https://huggingface.co/datasets/AIDroneMap/aidm-vineyard-small) v1 instead of Brighton Beach: 73 images of 20 megapixels instead of 18, pinned by commit and checked by SHA-256 on every run. They also check that the orthophoto is georeferenced where the images were taken. With a full build of the C++ dependencies, a release dry run takes 75 to 105 minutes instead of 65. The GPU test costs about USD 0.21 instead of 0.07.
- Test runs that publish nothing process a smaller set by default: [aidm-vineyard-ci](https://github.com/AIDroneMap/aidm-data/releases/tag/vineyard-ci-v1) v1, 32 images of aidm-vineyard-small v1 (two full flight lines, capture positions 34 to 65), copied byte for byte. `scripts/smoke-test.conf` pins both sets by URL and SHA-256, and `SMOKE_DATASET` picks one: `ci` (the default) for the smoke test of pull requests, release dry runs and local runs, `full` (the 73 images) for runs that publish a release and for benchmarks. `scripts/smoke-test.sh` and `scripts/gpu-smoke-modal.py` download a set from its URL, so a pin can point to a GitHub release as well as to Hugging Face, and keep downloaded zips in a cache folder named after their SHA-256. Evidence: `tests/test_gpu_smoke_modal.py` checks that both scripts read the same pins, that each pin is well formed, and how a set is picked and checked. The time a test run saves is not measured yet.
- The GPU image installs the GPU wheel of ONNX Runtime, `onnxruntime-gpu` 1.22.0 from `requirements-gpu.txt`, in place of the CPU wheel `onnxruntime` 1.22.1, so sky removal and background removal can use the CUDA provider. Its runtime stage moves to `nvidia/cuda:12.9.1-cudnn-runtime-ubuntu24.04`, pinned by digest, which adds cuDNN 9. No CUDA or cuDNN library comes from pip. The CPU image and `requirements.txt` do not change. The Modal GPU test does not assert this path yet. The GPU image is larger: its compressed size from the release dry run is recorded in #89, next to the 5.25 GB of the 0.1.0 GPU image. Evidence: the GPU image build fails if the CPU wheel is still installed, if the CUDA provider is missing or if it cannot find one of its libraries; the release dry run linked in #89 built the image.
- Sky removal and background removal log the ONNX Runtime provider their session chose, one line per session, in both images: `Sky removal: ONNX Runtime provider CUDAExecutionProvider`, or `CPUExecutionProvider`, and the same with `Background removal:`. ONNX Runtime falls back to the CPU when it cannot start CUDA, so this line replaces ` ?> Using provider`, which named the provider asked for. Evidence: `tests/test_onnx_provider.py`.

### Added

- The Modal GPU test asserts that feature matching runs on the GPU, so the OpenSfM GPU matcher counts as a GPU path ([ADR 0002](docs/adr/0002-gpu-paths-proven-by-the-release-test.md)). The test requires the engine's "Using GPU for image matching" line and OpenSfM's "Computing pair matching on GPU" line, and fails on OpenSfM's warning "GPU matching requested but CUDA is not available. Falling back to CPU FLANN." Each failure names the line it missed or found. Evidence: `TestCheckMatcher` in `tests/test_gpu_smoke_modal.py`, on lines of a real Modal job log and the fallback warning of the pinned OpenSfM source; the release dry run linked on [#88](https://github.com/AIDroneMap/aidm/pull/88).
- The Modal GPU test asserts that background removal runs on the GPU, so the ONNX filters count as a GPU path ([ADR 0003](docs/adr/0003-onnx-runtime-on-the-gpu-with-cudnn-from-the-base-image.md)). After the main run and its checks, the test runs the engine a second time on the same images, in its own project folder, with `--bg-removal --end-with dataset`. That run must exit 0 and log "Background removal: ONNX Runtime provider CUDAExecutionProvider". It fails on any other provider and on "Cannot load AI model". Each failure names the line it missed or quotes the line it found. The main run's options and outputs do not change. Evidence: `TestCheckBgRemoval` in `tests/test_gpu_smoke_modal.py`, on lines in the format the engine logs; the release dry run linked on [#92](https://github.com/AIDroneMap/aidm/pull/92).
- Every run of the release workflow (dry run, nightly, tag run) runs a golden comparison in the cpu-amd64, cpu-arm64 and gpu-amd64 jobs, after the smoke test ([ADR 0004](docs/adr/0004-golden-outputs-start-from-the-stored-dense-point-cloud.md)). It runs the tested image from `odm_filterpoints` to the end on the golden input, a stored project folder of aidm-vineyard-small v1 up to and including `openmvs`, and compares 18 outputs by SHA-256 with the lists in `scripts/golden-hashes/`, one per architecture. Any difference fails the job, and the job summary shows the file, the expected hash and the actual hash. `scripts/smoke-test.conf` pins the golden input by URL and SHA-256: release [golden-vineyard-small-v1-332c211b](https://github.com/AIDroneMap/aidm-data/releases/tag/golden-vineyard-small-v1-332c211b) of aidm-data. Compared: the filtered point cloud, the georeferenced LAZ (without its creation date), `dsm.tif`, the georeferencing files of the orthophoto, and the overlap preview of the report. The DSM preview and the camera positions export of the report are left out too, because their bytes depend on the runner's CPU. `scripts/golden-compare.py` lists each with its reason. Evidence: `tests/test_golden_compare.py`; the diagnostic in release dry run https://github.com/AIDroneMap/aidm/actions/runs/41016730652; the dry run of the comparison linked on [#93](https://github.com/AIDroneMap/aidm/pull/93).
- The engine checks the CPU at start. On a CPU below the minimum it stops with one line, for example `AIDM needs a CPU with AVX2 and FMA (2013 or later). This CPU does not have them.`, instead of crashing later with an illegal instruction.

### Fixed

- A split run with `--copy-to` copies only the merged results to the target folder (#77). Before, every submodel received `--copy-to` too and copied its own outputs there, because the list of options stripped before a submodel starts named the option with a hyphen while the keys it is matched against use an underscore. Every other option passed to submodels is unchanged. Evidence: `test_get_submodel_argv_drops_copy_to` in `tests/test_osfm.py` fails before the fix and passes after it.
- A block that fails during the orthophoto merge of a split dataset now fails the merge stage (#49). The error names the block's pixel rows and columns and the cause. Before, the merge logged a warning, skipped the block and reported success, so the merged orthophoto had a hole of up to 512 x 512 px. The partial output is deleted, so a rerun does not take it as done. Without failures the merged orthophoto does not change. Evidence: `test_failed_block_fails_merge` in `tests/test_orthophoto_merge.py` fails before the fix and passes after it, serial and with two workers; the byte-for-byte tests in the same file still pass.
- OpenMVS now detects arm64 as a 64-bit build, so `int_t`, `uint_t` and `Thread::safe_t` use 64-bit integers and the startup banner reports `x64` (#25). The dependency version, CPU targets and SSE settings do not change. Evidence: `tests/test_openmvs_width.py` checks the build-time header edit, repeat application and rejection of unexpected source.
- Engine builds fetch Eigen from the AIDroneMap mirror, including the Draco and LightGBM submodules and mvs-texturing's Eigen 3.3.2 download. All Eigen commits stay the same. CPU, GPU and native SuperBuild paths use the same settings. Evidence: `tests/test_eigen_mirror.py` and the GitLab-blocked no-cache CI builds linked in [issue #45](https://github.com/AIDroneMap/aidm/issues/45).
- The orthophoto merge feather pass no longer stops early by accident when the covered pixel count equals the block width (#13). Pixels change only in blocks where the old check fired. Evidence: `test_feather_blends_later_source_when_coverage_equals_block_width` fails before the fix and passes after it; `test_normal_merge_is_byte_identical_to_master` checks that a normal multi-source output stays byte for byte identical to master, both in `tests/test_orthophoto_merge.py`.
- On arm64, PoissonRecon no longer aborts with "Failed to close loop" in `odm_meshing`. It aborted on the first run of every arm64 smoke test in CI and finished only on a single-threaded retry (#24). The threads of its level-set extraction share plain `char` flags written next to plain data, which works on x86-64 only because x86-64 keeps stores in order. PoissonRecon is now built with its own `SANITIZED_PR` mode, which makes those flags and their data atomic; the pin and the source do not change. Evidence: ThreadSanitizer reports 107 data races in the build as it was and none with `SANITIZED_PR`, on the same synthetic point cloud. The smoke test now fails when the engine log shows a PoissonRecon retry, so the arm64 job of the release dry run checks the fix. The effect on meshing time is not measured yet.
- JPEG XL images get their EXIF metadata read again: make, model, GPS position, orientation and capture time. ODMExifRead, the EXIF library the engine uses since ODX dropped upstream ExifRead, does not know the JPEG XL container and returned no tags, so JPEG XL datasets lost their GPS positions (#12). The engine now finds the Exif box of the container itself and hands its TIFF block to the library.
- The arm64 image now has OpenCV's NEON_DOTPROD and NEON_FP16 kernels, which OpenCV runs on CPUs that support them. The compiler wrappers dropped the `-march=armv8.2-a+dotprod` and `-march=armv8.2-a+fp16` flags OpenCV builds them with, so the arm64 build had no dispatched kernels at all (#10). The smoke test on the GitHub arm64 runner shows no measurable change: opensfm took 51.8 s and 51.5 s before the fix and 51.5 s after.
- The release workflow accepts the manifest digest as proof that the pushed image is the tested one. Docker 29 on the GitHub runners uses the containerd image store, which reports that digest instead of the config digest, so every GPU image check failed from 26 October 2026.
- The cut and feathered orthophotos of split-merge submodels (`odm_orthophoto_cut.tif`, `odm_orthophoto_feathered.tif`) are computed in windows of about 4 megapixels instead of whole bands. On a 181 megapixel orthophoto the engine process peaks at 1.5 GiB instead of 4.1 GiB in the orthophoto stage, and the files are byte-identical.
- Orthophoto merge in split-merge runs stops reading the remaining submodels in its first pass once a block is fully covered. The check compared the covered pixel count with the block width instead of the block area, so it almost never stopped early. The merged pixels do not change.
- With `--bg-removal`, a failure to make a mask for one image logs "Cannot generate mask for <image>" again. Before, it raised a `NameError` and stopped the dataset stage.
- When the point classification model cannot be downloaded, the warning names the model URL. Before, a `NameError` hid the cause behind a generic "Cannot classify using OpenPointClass" warning.
- The GPU image no longer starts `PYTHONPATH` with an empty entry, which made Python import from the current directory.
- When PoissonRecon aborts in a parallel run, the engine retries it once, serially, instead of halving the thread count until it reaches one. PoissonRecon's parallel loops use every CPU whatever `OMP_NUM_THREADS` says, so each halved retry repeated the run that had failed: with `--max-concurrency` 15, one abort cost three failed runs before the serial one (#24). The warning names the thread count that failed, for example "PoissonRecon failed with 14 threads, let's retry with 1...". It used to log twice the new count, so a failure with 7 threads read "failed with 6 threads". Evidence: `tests/test_mesh.py`.

## 0.1.0

The first AIDM release, based on the ODX 3.8.4 engine. Processing is unchanged, so results match ODX 3.8.4, and this release makes no performance or accuracy claims. What is new is how the engine is built, tested and shipped.

### Highlights

- **Every image is tested before it is published.** Each release image processes a real survey of 18 drone images from start to finish, and is published only if the orthophoto, elevation model, point cloud and textured model all come out. This covers the CPU image on x86-64 and arm64, and the GPU image on a real NVIDIA GPU as well as on a machine without one.
- **What you pull is what was tested.** The release workflow checks that each published image is the exact image that passed, and the release notes list the digests.
- **One GPU image for any machine.** The GPU image uses CUDA when an NVIDIA GPU is present and falls back to the CPU when it is not. Before, it needed an NVIDIA GPU to start at all.
- **You always know what you run.** Logs, `--version`, the PDF report and GeoTIFF metadata show `AIDM 0.1.0 (ODX 3.8.4)`, and AIDM API reports both versions in `GET /info`.

### Changed

- The engine calls itself AIDM. The log banner, `--version`, `--help`, the PDF report and the Software tag of GeoTIFF outputs show `AIDM 0.1.0 (ODX 3.8.4)`.
- `VERSION` holds the AIDM version, `0.1.0`. The ODX version it is based on is in the new `UPSTREAM_VERSION` file.
- `log.json` reports `"engine": "AIDM"` and `0.1.0` in `version` and `odmVersion`. A new field, `upstreamVersion`, holds `ODX 3.8.4`.
- A new `ENGINE` file holds `aidm`. AIDM API reports it as the engine name in `GET /info`.
- `benchmark.txt` and the EXIF Software tag of frames extracted from video say AIDM.
- The CPU image is built for a generic CPU, as the GPU image already was. It runs on machines older than the one that built it.
- Both images carry OCI labels for source, version, licence, title and description.
- The GPU image also runs on machines without a GPU, on the CPU. It ships the CUDA stub driver library as a fallback for OpenMVS; the real driver replaces it when the container runs with `--gpus`.
- Every release run tests the GPU image on a real NVIDIA GPU on Modal and checks that the engine uses it. The images are only tagged when this test passes.

### Removed

- The Windows and macOS build files inherited from ODX, which were not maintained: `*.bat`, `innosetup.iss`, `configure_macos.sh`, `portable.Dockerfile`, `vcpkg.json` and `vcpkg-requirements.txt`. The CPU `Dockerfile` now builds what `portable.Dockerfile` built.

### Fixed

- The build downloads Ceres Solver from its GitHub release first, and falls back to ceres-solver.org. The site timed out on the build runners and stopped every image build.

### Not changed

- Command-line options, `settings.yaml` keys and defaults, output files and folders, stage names and Python modules are the same as in ODX 3.8.4.

### Known limitations

- No performance or accuracy changes compared to ODX 3.8.4 yet.
- Images are for Linux only. The CPU image runs on x86-64 and arm64, the GPU image on x86-64 only.
- `configure.py`, the Windows configure script from ODX, is still in the repository. It no longer works, because the vcpkg files it reads are gone.
